# v0.6 Pattern Learning Engine —— 检索接库实施方案

> 状态：方案草案（2026-10-26 盘点产出，待用户确认后实施）
> 依据：`AGENTS.md` 9.3 待办 14 / 17 / 20
> 版本号权威来源：`docs/roadmap.md` 第 3 节（v0.6 = Pattern Learning Engine，Planned）

---

## 一、为什么要做：三层数据各说各话

项目里现在有三份「知识」，彼此不通气：

| 层 | 载体 | 规模（2026-10-26） | 谁在用 |
|---|---|---|---|
| 卡片层 | `comfyui_library/knowledge/nodes/*.md` + `_consolidated/*.md` | 7,248 张知识卡 / 9,437 个模式 | `engine/retrieval` 倒排索引 |
| 记录层 | `comfyui_library/workflows/learning/*.md` | 74,209 条学习记录 | `engine/knowledge_graph` 直读 |
| 结构层 | `comfyui_library/database/storage/*.sqlite` + 三个派生索引 | 74,208 workflow / 74,208 experience / 7,302 node | **无人消费** |

检索（`retriever.retrieve`）只答「这个节点是什么 / 这类流程长什么样」，
图谱（`_collect_graph_facts`）答「谁用了它 / 它常和谁一起出现」，
但**「哪些工作流出过这类问题」「哪些工作流用了这个节点」这两类跨条目事实，
在结构层里躺着一个 2GB 的数据库，检索层完全看不到。**

这就是待办 20 的实质：**检索层不查库**。

## 二、三项待办的根因

### 待办 20（引擎接库收尾）— 检索层与数据库零连接

现状确认：

- `engine/retrieval/retriever.py` 的 `build_index()` 扫的是 Markdown 卡片，
  落盘 `retrieval_store.json`（倒排索引），**从不读 `database/storage/`**。
- `engine/knowledge_graph/__init__.py:build_graph()` 的三个数据源是
  `LearningStore.completed_records()`（Markdown）、`KnowledgeStore.load_all()`（Markdown）、
  `load_node_index()`（JSON），**同样不消费派生索引**。

后果：结构层的三张索引（`workflow_index.json` / `node_index.json` / `pattern_index.json`）
只由 `IndexManager` 写、无人读，等于付了 2GB 存储成本却没换到检索能力。

### 待办 17（图谱接进检索与回答）— 问题边与多跳路径未接

图谱模型里**已经有**三条问题相关边（`engine/knowledge_graph/__init__.py:47-49`）：

```
workflow -[has_problem]-> problem
problem  -[suggests]->   solution
problem  -[problem_in]-> node
```

但 `_collect_graph_facts()`（`engine/agent_core/agent.py:444`）只消费了三类事实：

1. 概念命中（`concept` 节点 → 使用者 + 标志性节点）
2. 节点使用者（`workflows_using`）
3. 共现伙伴（`_top_co_partners`）

`problem_in` 边建了但没读；多跳路径（workflow → problem → node → 共现节点）没有遍历逻辑。

### 待办 14（RAG v0.4 实装）— 键名与内容拼装

| 工具 | 现状 | 问题 |
|---|---|---|
| `rag/tools/prepare_documents.py` | `"content": str(item)` | 把整个 item 的 Python repr 塞进 content，检索时噪声极大 |
| `rag/tools/build_index.py` | 产出 `{"text": ..., "metadata": ...}` | 键名 `text` |
| `rag/tools/search_database.py` | 读 `doc["content"]` | 键名 `content` |

另：embedding 接入需要外部模型，当前是纯关键词倒排。

## 三、分步实施方案

### 第 1 步：库侧只读适配层（不写库，安全） — ✅ 已完成 2026-10-26

> **2026-10-26 实测校正**：三个派生索引的真实语义与预想有出入，实施前必读。

**产出**：`engine/retrieval/db_facts.py`（门面类 `DatabaseFacts`）
**测试**：`engine/test_db_facts.py` — 22 项断言全通过（含只读约束验证）

| 索引 | 真实键 | 真实值 | 大小 |
|---|---|---|---|
| `node_index.json` | 节点名（7,302） | `{category, used_in: [文件路径…], usage_count}` | 187.3MB |
| `workflow_index.json` | 节点名（7,301） | `[文件路径…]`（与 node_index 的 used_in 重复） | 180.3MB |
| `pattern_index.json` | 模式名（9,604） | `{workflows: [路径…], workflow_count, description}` | 9.8MB |

**三个索引全是「节点/模式 → 文件路径」，没有一个是「workflow id → 属性」。**
所以能支撑的查询只有：

```python
def workflows_using_node(node_name) -> List[str]   # ✅ node_index.used_in
def patterns_for_workflow(workflow_id) -> List[str]  # ✅ pattern_index 反查
def workflows_with_problem(problem_key) -> List[str]  # ❌ 无此索引，需另建
```

**已实现的 API**（`DatabaseFacts`）：

```python
workflows_using_node(node_name) -> List[str]   # 用了某节点的工作流 ID
node_usage_count(node_name) -> int
node_category(node_name) -> str
all_node_names() -> List[str]
workflows_with_pattern(pattern_name) -> List[str]
patterns_for_workflow(workflow_id) -> List[str]  # 反查
pattern_description(pattern_name) -> str
all_pattern_names() -> List[str]
workflows_with_problem(problem_key) -> List[str]  # 诚实返回空（见下）
```

**关键设计决策**：

1. **路径 → ID 转换在内部完成**。索引里存的是长路径文本，
   调用方不该被迫做字符串解析。ID 提取支持正/反斜杠、位数校验、去重，
   且**兼容两种命名**：`某某工作流_2087218383308812289.json`（多数）
   和裸 ID 的 `2029394586908499969.json`（10-09 那批历史落盘）。
2. **`workflows_with_problem` 诚实返回空**。problem 维度当前**没有索引**，
   返回一个「看起来有结果其实残缺」的列表会让上层误判「没有工作流出过这个问题」。
   待办 17 需要先在图谱侧落一份 problem 维度正排索引。
3. **索引懒加载 + 只缓存最近一个**。node_index 187MB 不能常驻内存，
   也不该每次查询重读盘。
4. **全程只读**。测试验证了调用后 sqlite 主库 mtime 与索引 mtime 均不变，
   且以 `mode=ro` 打开——管线运行时可安全调用，不触发 AGENTS.md 2026-10-19 的同写禁令。

**三个口径必须分清**（实测踩出来的）：

| 口径 | 含义 | 例子（`Any Switch (rgthree)`） |
|---|---|---|
| `usage_count` | 索引里的总引用数，**含官方模板** | 2,194 |
| `real_workflow_count()` | 能解析出 ID 的真实工作流数 | 2,190 |
| 模板引用 | 官方模板路径（`comfyui-workflow-templates-json/…`），文件名是英文模板名，无工作流 ID | 4 |

另外 `node_index` 里有 **190 个 UUID 形态的键**（`010af74f-5a21-…`），
那不是节点名而是**官方模板条目**，其路径全是英文模板名。
调用方查节点时要能区分这类键，否则会拿到「ID 数为 0」的怪异结果。

**计数差额的完整解释**（以 `LoadImage` 为例，实测 58,215）：
```
58,215 = 57,815（去重后的真实 ID）
       +   376（无 ID 路径，其中 370 是官方模板）
       +    24（跨标签重复：同一 ID 出现在多个标签目录）
```
跨标签重复是常态——同一个工作流在站点上跨标签出现，
落盘时会在多个标签目录各存一份。

**顺带发现一处 180MB 冗余**：`workflow_index.json` 的值就是 `node_index.json`
的 `used_in` 字段去掉外层包装（两边路径计数完全相同：官方模板 3,729 + 真实 1,684,995）。
它本该存精简的 `workflow_id`，实际存的是**长路径文本**——这与待办 22
（junction 表换整数外键）是同一个病根在索引层的表现。
建议在实施第 1 步时一并处理：要么让 workflow_index 真正存 id，要么直接删掉它
（检索层改用 node_index 即可，省 180MB）。


### 第 1.5 步（实测新增）：确认消化链路的全库覆盖性

> **2026-10-26 实测**：这是 v0.6 能否受益的前提——若新学的工作流只进到某个标签目录，
> 消费侧就接不到。

`learn_pipeline.py --tag X --skip-collect --skip-download` 的实际范围：

| 步骤 | 实现 | 范围 |
|---|---|---|
| 收集 | `--skip-collect` | 跳过 |
| 下载 | `--skip-download` | 跳过 |
| 入库 | `import_workflows.py` 的 `DEFAULT_SOURCE` | **全库** `download/workflows-by-tag` |
| 学习 | `learn_folder()` 无参 → `WORKFLOWS_DIR` | **全库** `comfyui_library/workflows/` |

**结论**：`--tag` 只影响收集/下载步。消化轮是**全库口径**，
所以一轮消化即可覆盖所有标签的新增文件，v0.6 消费侧能一次看到全部新数据，
不需要为每个标签单独入库。


### 第 2 步：agent_core 接入库事实 — ✅ 已完成 2026-10-26

**产出**：
- `engine/agent_core/agent.py` 新增 `_collect_db_facts()` / `_db_facts()`
- `engine/agent_core/state.py` 新增 `db_facts` 字段
- `engine/agent_core/config.py` 新增 `enable_db_facts` / `db_facts_limit`（默认 4）
- `engine/test_agent_db_facts.py`（15 项断言全通过）

**三条硬约束**：

1. **全程只读**。只消费派生索引，不碰 sqlite 主库——管线运行时也能安全调用，
   不触发 AGENTS.md 2026-10-19 的同写禁令。
2. **独立限流、独立成节**。库事实与 `graph_facts` 分开存放、分开限流，
   回答里分「跨条目知识图谱」和「结构层库事实」两节，读者能分清依据来源。
3. **可降级**。索引是运行期产物，可能不存在或为空；此时静默跳过并记
   `stages_skipped`，绝不让「查不到」变成链路报错。

**新增能力**：

| 维度 | 问题 | 能答什么 |
|---|---|---|
| 节点 | 「KSampler 怎么用」 | 该节点在全库被多少工作流使用 + 使用者 ID 预览 |
| 工作流 | 「这个流程算哪种模式」 | 当前工作流命中了哪些已归纳模式 |

**实现中踩到的坑**：一开始在 `_collect_db_facts` 里调了 `state.add_stage("db_facts")`，
结果 `stages_run` 变成 `[..., 'db_facts', 'retrieve', ...]`——**库事实采集是
retrieve 阶段内部的一步，不是独立阶段**，单独记阶段位会打乱顺序，
被 `test_agent_core` 的阶段顺序断言当场抓到。改为不记入 `stages_run`，
事实只落在 `state.db_facts`。

**验收**：`python -m engine.test_agent_core` 全部通过（含真实模块端到端 B2）；
`python -m engine.test_agent_db_facts` 15 项全通过。

### 第 3 步：图谱建图改吃派生索引 — ⚠ 方向被实测推翻，需重新设计

> **2026-10-26 实测：这条设计方向在数据层面不成立。**
> 原设想「`build_graph()` 改吃派生索引，替代直读 76,726 个 Markdown」——
> 问题是派生索引里**没有建图需要的字段**。

**为什么不行**：`GraphBuilder.build(records, patterns)` 需要的 `records`
是完整的 `LearningRecord` 对象，每个 workflow 要带：

```python
workflow_name / workflow_type / status / source_kind / official /
coverage / nodes（完整节点清单）/ patterns / learned_at / file_path
```

而三个派生索引存的是「节点名/模式名 → **文件路径列表**」——
只有路径，没有 name、没有 coverage、没有 nodes、没有 learned_at。
**改数据源等于要把索引整个重建**，成本远超收益。

**那「图谱建图慢」这个问题怎么解**：

| 思路 | 评估 |
|---|---|
| ① 建图改吃派生索引 | ❌ 不可行（缺字段，见上） |
| ② 建一个 **workflow 属性正排索引** | ✅ 可行，但这就是「新建索引」——本来想避开的工作 |
| ③ 让图谱**增量更新**，只处理新增/变更的 workflow | ✅ **这是正解** |
| ④ 缓存 LearningRecord 的解析结果（pickle/sqlite 旁表） | ✅ 可行，与 ③ 互补 |

**推荐路径**：③ + ④ 组合——
- 增量更新：图谱构建时对比上次图的 workflow 集合，只处理新增/变更部分
  （本次新增 2,517 个 = 全量的 3.4%，增量后建图从 30 分钟降到 1-2 分钟）
- 解析缓存：Markdown 解析（frontmatter → LearningRecord）是纯 CPU 开销，
  缓存成 pickle 后二次建图几乎零成本

**注意**：③ 需要图谱构建器支持「增量合并」语义——
现在的 `builder.build()` 是全量重建并覆盖保存。改成增量要先想清楚
「删除的工作流怎么处理」（图谱里对应的顶点要清理），
这是个有设计成本的重构，不适合顺手做。

**问题边（`problem_in` / `has_problem`）的调研结论**：

全库 76,726 条学习记录里，24,946 条（32.5%）含 `problems`，
但**问题种类只有 3 种**，分布极度集中：

| 问题描述 | 出现次数 |
|---|---|
| Steps较低，可能导致细节不足 → 建议增加到20-30 | 32,975 |
| 发现KSampler但没有VAEDecode → 添加VAEDecode完成latent转换 | 805 |
| CFG值较高，可能导致Prompt约束过强 → 建议尝试CFG 7-10 | 4 |

严重度分布：medium 32,979 / high 805。

**这意味着**：即便落了 problem 维度正排索引，「哪些工作流出过这类问题」
的答案也只有 3 种不同结果——99% 都是「Steps 较低」。作为检索信号，
它几乎不携带区分度。**所以「必须先落 problem 索引才能做第 3 步」这个
前置条件并不成立**，而且问题边本身的价值也很有限。

**真正值得做的问题边**：不是「哪些工作流有这个问题」（没区分度），
而是「**这个问题出在哪个节点上**」（`problem_in` 边的语义）——
比如「哪些节点最容易出 Steps 较低」。但当前诊断引擎只产出
Steps/CFG/VAEDecode 三类固定问题，且不标注问题落在哪个节点上，
这个数据源本身就不存在。要做需要先改诊断引擎。

### 第 4 步：RAG 工具键名与内容拼装 — ✅ 已完成 2026-10-26

**产出**：
- `skills/comfyui-learning/rag/tools/prepare_documents.py` 重写
- `skills/comfyui-learning/rag/tools/build_index.py` 重写
- `skills/comfyui-learning/rag/tools/search_database.py` 重写
- `engine/test_rag_tools.py`（31 项断言全通过）

**三处修复**：

1. **`content` 不再是 `str(item)`**。原来正文是
   `{'name': 'KSampler', 'usage_count': 42}` 这种 Python repr，
   检索命中的全是引号括号噪声。现在按 `rag_rules.md` 的 Document Types
   拼装规范正文：

   ```
   Wan Character Video
   category: video_generation
   nodes: WanVideoLoader、KSampler
   models: Wan2.1
   description: 角色一致性视频生成
   parameters: steps: 20；cfg: 7.0
   ```

   三类文档各一套字段映射（workflow / node / model），且**每类都带别名表**——
   同一个语义在不同来源里叫法不同（`name` / `workflow_name` / `title`），
   别名表让拼装对数据来源变化更鲁棒。

2. **键名统一为 `content`**。原 `build_index` 产出 `text`、`search_database`
   读 `content`，两边对不上——**检索永远读不到正文**。现在统一为 `content`，
   同时保留 `text` 作为兼容别名，历史落盘的索引文件不必重跑。

3. **匹配更宽容**。原来只做整串 `query in content`，查询词必须整串出现。
   现在拆词元后逐个匹配（全命中即算命中），搜「latent 解码」也能命中
   正文里分散描述的文档。

**导入方式说明**：`skills/` 目录带连字符且不是 Python 包（无 `__init__.py`），
测试里用 `importlib` 按文件路径加载，不走常规 import。

**embedding**：留接口不接实现——需要外部模型服务，属用户侧依赖。

## 四、风险与护栏

| 风险 | 护栏 |
|---|---|
| 与管线抢写 sqlite | 第 1 步只读派生索引，**全程不写库**；实施期间不跑 learn_pipeline |
| 图谱改数据源导致劣化 | 新旧图谱三项对照验收（顶点数 / 边数 / matches 匹配率） |

## 五、与数据层的关系

v0.6 不改学习引擎的产出格式，只改**消费侧**。
所以它与 10-26 的数据补收（消化 → 重归纳 → 图谱重建）互不冲突：
数据层先收干净（当前正在做），消费侧随后接上，顺序不能反——
否则新学的 2,458 + 新下载的 2,594 个工作流仍然进不了检索。
